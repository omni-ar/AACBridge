\begin{abstract}
A language model running on a phone often needs a description of the user's situation (where they are, who is with them, what time of day it is) before it can answer usefully. Feeding that description in with every request is expensive: on our test phone, the prefill step for a 439-token prompt took 14.2~s. Server systems avoid repeated prefill by reusing cached key-value (KV) state across requests, but that depends on many users sending overlapping prompts. A single phone has no such request stream. It does, however, have sensors. We present CAP-KVC, which uses GPS, Bluetooth Low Energy (BLE) proximity and time of day to rank a small set of pre-written contexts, prefills the likely ones while the device is idle, and keeps at most three of them resident as llama.cpp KV state. At interaction time only the user's intent tokens are decoded. On a OnePlus~11R running Qwen2.5-0.5B-Instruct (Q4\_K\_M), resuming a restored 44-token context took 351~ms of prefill versus 2507~ms for decoding the same context inline (7.1$\times$, $n=30$ each); restoring the state took 2.4~ms. Over 100 synthetic days of sensor traces with five contexts, the deployed routing and residency rules used the correct context for 98.5\% of 6,400 interactions, against 92.2\% for a request-driven cache without sensing, which misses on every first visit. We also report what this costs: 1.5\% of interactions used the wrong context, and an attacker who can forge GPS without detection raised that to 38.9\%. The evaluation covers one device, one model, five contexts and synthetic traces.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Small instruction-tuned models now run entirely on phones once quantized to 4~bits~\cite{dettmers2022,frantar2022,llamacpp}. For many assistive uses the model is not useful on the user's words alone. An augmentative and alternative communication (AAC) app~\cite{beukelman2020}, for instance, receives a short intent such as ``I need water'' and is expected to expand it into something that fits the setting: a hospital ward at 11~a.m. is different from home in the evening with a caregiver present. The usual way to provide this is to put a context description in front of the intent and let the model read both.

Reading the context is the prefill step: one forward pass over all prompt tokens before the first output token appears. Its cost grows with prompt length. On the phone used in this paper, prefill took 2.5~s for a 52-token prompt and 14.2~s for 439 tokens (Section~\ref{sec:eval_latency}), roughly 30~ms per token. For a user who communicates through the device, that delay sits in the middle of every turn.

Datacenter serving systems handle the same problem by not recomputing prefixes they have already seen. SGLang keeps prompt prefixes in a radix tree~\cite{sglang}, vLLM shares KV blocks between requests~\cite{vllm}, Prompt Cache stores attention states for reusable prompt modules~\cite{promptcache}, and RAGCache caches the KV state of retrieved documents across requests~\cite{ragcache}. All of these are request-driven: the cache is filled when a request containing the prefix arrives, and it pays off when later requests share that prefix. That works on a server handling many users. On a phone used by one person, the request that would populate the cache is the user's own first turn in a new setting, and that turn pays the full prefill cost.

A phone does have information a server lacks: its sensors usually reveal the setting before the user says anything. CAP-KVC (Context-Aware Predictive KV-Cache priming) uses this. A small set of contexts is written in advance. A background sweep scores them against GPS position, nearby BLE devices and time of day, prefills the highest-ranked ones while the device is idle, and keeps their KV state resident. When the user acts, the app resumes from the best resident context and decodes only the intent. The hypothesis we test is that sensor readings predict the needed context often enough for this to beat request-driven reuse, at an acceptable rate of wrong-context answers.

This paper makes three contributions:
\begin{enumerate}
\item A sensor-driven predictive KV caching design for a single user: deterministic context scoring, a bounded resident set with hysteresis-gated replacement, and a two-tier fallback when no relevant state is resident.
\item An Android implementation on llama.cpp with per-slot KV residency, rollback of each interaction so a resident state is reused unchanged, crash-safe cache persistence, and location input validation.
\item An evaluation that separates the restore benefit (matched-context latency) from prediction quality (trace-driven comparison against oracle, request-driven, random and single-sensor baselines) and from adversarial sensor input.
\end{enumerate}

\section{Related Work}
\label{sec:related}

\textbf{Reusing KV state across requests.}
RadixAttention in SGLang~\cite{sglang} matches incoming prompts against a radix tree of cached prefixes and evicts by LRU. PagedAttention~\cite{vllm} lets requests share KV blocks. Prompt Cache~\cite{promptcache} precomputes attention states for prompt modules that applications reuse, and CacheBlend~\cite{cacheblend} combines cached chunks that are not prefixes. RAGCache~\cite{ragcache} caches the KV state of retrieved documents in a GPU/host hierarchy and replaces entries with a policy that accounts for retrieval patterns and recomputation cost, outperforming LRU. CacheGen~\cite{cachegen} compresses KV state for network transfer. These systems decide what to keep after seeing requests. CAP-KVC decides what to compute before the request exists, from sensor evidence, which is the only signal available ahead of the first request on a single-user device (Table~\ref{tab:positioning}). We do not run SGLang or RAGCache themselves; they target GPU servers. Section~\ref{sec:eval_prediction} instead simulates their request-driven policy (LRU over contexts identified at request time) on the same traces.

\textbf{Shrinking the KV cache.} H$_2$O~\cite{h2o}, Scissorhands~\cite{scissorhands}, SnapKV~\cite{snapkv}, StreamingLLM~\cite{streamingllm} and KVQuant~\cite{kvquant} reduce KV memory within a sequence. They are complementary: a compressed state can still be primed and restored.

\textbf{On-device inference.} Quantization~\cite{dettmers2022,frantar2022}, small-model design~\cite{mobilellm}, mobile runtimes~\cite{llamacpp,mlcllm}, flash offloading~\cite{llminaflash} and heterogeneous NPU/CPU execution~\cite{powerinfer2} make phone inference feasible. They lower the cost of each token but do not remove the prefill of a long context from the interaction path.

\subsection{Problem}
Let $C=\{c_1,\dots,c_M\}$ be pre-written contexts with prompts $p_i$ of $N_i$ tokens. Inline (retrieval-augmented style) inference decodes $p_i$ followed by the intent $q$ on every request, so prefill costs grow with $N_i+|q|$. CAP-KVC moves the prefill of $p_i$ to idle time and stores its KV state; at interaction time it restores the state and decodes only $q$. The open question is which $p_i$ to prepare, since memory allows only $K<M$ resident states. The prototype has $M=5$ contexts (home morning, home evening, hospital ward, therapy room, caregiver visit) and $K=3$.

\subsection{Context Scoring}
\label{sec:scoring}
Each context $c_i$ has an expected hour $t_i$, an anchor location $\ell_i$ and a set of BLE anchors $A_i$ with weights $w_{ij}$. For a sensor snapshot the score is
\begin{equation}
S(c_i)=\alpha S_{\mathrm{time}}+\beta S_{\mathrm{gps}}+\gamma S_{\mathrm{ble}},\qquad \alpha+\beta+\gamma=1,
\label{eq:score}
\end{equation}
with
\begin{align}
S_{\mathrm{time}}&=\exp\!\bigl(-d_{\mathrm{circ}}(t,t_i)^2/2\sigma^2\bigr),\quad \sigma=2~\mathrm{h},\\
S_{\mathrm{gps}}&=\exp\!\bigl(-d_{\mathrm{hav}}(\ell,\ell_i)/\lambda\bigr),\quad \lambda=0.1~\mathrm{km},\\
S_{\mathrm{ble}}&=\textstyle\sum_{j\in A_i} w_{ij}\,\mathbb{1}[j\ \mathrm{seen}] \big/ \sum_{j\in A_i} w_{ij}.
\end{align}
$d_{\mathrm{circ}}$ wraps around midnight, so $S_{\mathrm{gps}}$ falls to 0.37 at 100~m. The weights come from per-sensor reliability, normalized to sum to one: time has a fixed weight $w_t=0.4$; GPS has $w_g=\exp(-a/50~\mathrm{m})$ for reported accuracy $a$, or 0 without a fix; BLE has $w_b$ equal to the mean of $1/(1+e^{-0.1(r+70)})$ over observed RSSI values $r$, or 0 if nothing is seen. Contexts scoring below 0.01 are dropped. The scorer has no learned parameters; ``predictive'' refers to preparing a context before the request, not to a trained model.

\subsection{Residency and Hysteresis}
\label{sec:residency}
The resident set holds at most $K=3$ KV states. After each sweep, candidates are taken in rank order. A candidate already resident is kept; otherwise it takes a free slot, or replaces the weakest resident state if its score exceeds that state's score by more than $\Delta$. $\Delta$ is a hysteresis margin on scores. It is unrelated to $K$; the submitted version of this paper conflated the two and justified $\Delta$ with an unrelated text-similarity experiment, which we drop. The deployed value is $\Delta=0.10$; Section~\ref{sec:eval_hysteresis} measures its effect. The same rule runs in the 60-second sweep and in a 15-minute background check that sees no BLE data and may only add the top-ranked context.

\subsection{Interaction and Fallback}
At interaction time the app uses the highest-ranked context that is resident. If none is, the interaction is a cold miss: a canned response is shown immediately (Tier~1) and priming of the current top contexts starts in the background (Tier~2). A wrong-context answer happens when a resident context is used but is not the true one.

\section{Implementation}
\label{sec:implementation}

AACBridge is an Android app (Kotlin, API~26+, \texttt{arm64-v8a}) using llama.cpp~\cite{llamacpp} through JNI, with Qwen2.5-0.5B-Instruct~\cite{qwen25} quantized to Q4\_K\_M.

\textbf{Native boundary.} The JNI layer exposes 14 functions, all with scalar arguments and results: lifecycle (initialize backend, load model, release), KV operations (save, load, clear scratch, reset slot), inference (inline run, prefill only, resume) and four timing getters. A single \texttt{ReentrantLock} serializes every native call, because llama.cpp context state is shared.

\textbf{Sequence slots.} The llama.cpp context is created with four sequences of 1024 tokens: three for resident states and one scratch sequence for inline inference and benchmark restores, so neither disturbs a resident state. Priming decodes a context directly into the slot assigned to it and serializes that slot to a temporary file, which is then renamed into place, so a crash cannot leave a partial cache file. Resuming appends the intent at the slot's current position and, after generation, removes everything after the cached context, so the resident state is reused unchanged by the next interaction. With 24 layers, 2 KV heads of dimension 64 and fp16 storage, Qwen2.5-0.5B needs 12~KiB of KV per token; the four sequences reserve 48~MiB at context creation. We did not re-measure process memory after this layout change.

\textbf{Sensing.} A foreground service runs the sweep every 60~s: a 3-second BLE scan and a location fix. Each provider's last fix is validated (not flagged as mock by the OS, at most 120~s old, reported accuracy between 2 and 500~m); if none passes, one fresh fix is requested, preferring the network provider over GPS. A WorkManager job runs every 15~minutes without BLE scanning.

\textbf{Intent input.} Intents come from on-screen buttons or a gaze-dwell interface; an sEMG+gaze fusion classifier from earlier work is included as a prototype input but is not evaluated here.

\textbf{Backup.} The manifest disables app backup and excludes the KV cache directory from cloud backup and device-to-device transfer.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Setup}
Latency was measured on a OnePlus~11R (Snapdragon~8+~Gen~1, 8~GB RAM, Android~14) with 4 threads, batch 512, greedy decoding and at most 64 output tokens. Each condition ran 2 warm-up and 30 measured trials. Prefill and generation times come from \texttt{std::chrono} timestamps around \texttt{llama\_decode} in native code; restore time is measured around the load call. All 180 trials and the analysis script are in the repository.

During this run the phone's gaze interface remained active and issued 45 interaction inferences between trials. These held the engine lock, and the trial timer started before the lock was taken, so the end-to-end totals of some trials include waiting time. We therefore report only the natively timed components, which the lock wait does not affect, and not end-to-end totals. The app now blocks interaction inference during benchmarks and starts trial timers after taking the lock.

\label{sec:eval_latency}

With the context matched, mean prefill fell from 2507~ms (SD 522) to 351~ms (SD 97), a ratio of 7.1 (Welch $t(31.0)=22.2$, $p<10^{-19}$; Mann--Whitney $p<10^{-10}$; Table~\ref{tab:latency}). Restoring the state took 2.4~ms on average (median 1.2~ms). A rough time to first token, taken as restore plus prefill plus one mean generation step, is about 0.43~s for CAP-KVC and 2.6~s inline. Inline prefill grew by about 30~ms per prompt token (OLS, $R^2=0.91$; Fig.~\ref{fig:prefill}), reaching 14.2~s at 439 tokens, where the CAP-KVC prefill was 40.5$\times$ shorter. That larger ratio compares different context lengths and reflects the cost CAP-KVC avoids when contexts are long, not a matched speedup. We measured restore only for the 44-token cache, so we cannot say how restore time grows with context length.

Generation dominates the full response. With 64 output tokens, generation took 4.4--8.6~s (medians), so the 2.1~s saved in prefill at matched length shortens the complete response far less than the prefill ratio suggests. The benefit is concentrated in time to first token. Generation times varied between conditions and trials (IQRs above 1~s); the run recorded no thermal or CPU-frequency data, so we cannot attribute this variation.

\subsection{Prediction and Cache Policy}
\label{sec:eval_prediction}
\textbf{Traces.} We have no recorded sensor traces from users, so we use synthetic ones (seed 42). Each of 100 days follows the five-context routine 06:00--22:00, with every context boundary shifted per day by $U(\pm0.5~\mathrm{h})$. A sweep runs every minute and an interaction every 15 minutes (6,400 interactions). Each sweep draws GPS displacement $\mathcal{N}(0,50~\mathrm{m})$, GPS dropout 10\%, reported accuracy $\mathcal{N}(15,10)$~m, per-beacon detection 80\% with RSSI $\mathcal{N}(-65,10)$~dBm, BLE outage 15\%, and a spurious beacon 10\% of the time. The high-noise setting uses $\pm1.5$~h shifts, 200~m GPS noise, 30\% GPS dropout, 50~m accuracy, 50\% detection and 40\% BLE outage. The context time anchors were written from the same routine, so time-of-day evidence is favourable by construction.

\textbf{Simulation.} The evaluator calls the production scoring, residency and selection code. It does not model priming delay: a state chosen at one sweep is assumed usable by the next minute.

\textbf{Metrics.} For each interaction with true context $c^\ast$ and used context $\hat{c}$: correct if $\hat{c}=c^\ast$; wrong context if $\hat{c}\neq c^\ast$; cold miss if no ranked context is resident. These three partition the interactions. We also report loads per day (states primed or restored into the resident set), which measures churn.

\textbf{Baselines.} \emph{Oracle}: $c^\ast$ is always resident, giving the restore benefit with perfect prediction. \emph{Request-driven LRU}: no sensing; the context becomes known when the request arrives (the best case for request-driven reuse), is used if cached, and is otherwise a cold miss and inserted into a three-entry LRU cache that persists across days. \emph{Random}: uniform random scores each sweep, same residency rule. \emph{Single sensor}: time only (no GPS or BLE), and GPS only or BLE only with $w_t$ reduced to 0.001 so that time does not leak in through normalization.

Table~\ref{tab:prediction} shows the results. With all sensors the deployed rules used the correct context for 98.5\% of interactions. The request-driven LRU baseline never used a wrong context but missed 7.8\% of interactions, one at each of the five daily context changes, because five contexts visited in order never fit in three entries. Sensing removed those misses at the price of 1.5\% wrong-context interactions. Each sensor alone did worse than the combination: GPS cannot separate the three contexts that share the home coordinates, and with BLE alone the router produced no candidate in 0.5\% of interactions, when no registered beacon was seen. Time alone reached 92.2\%, which reflects how the traces were built rather than a property of real schedules.

Cold misses were near zero for every sensing policy, and in every sensing configuration the router's top-1 accuracy equalled the share of correct interactions. With three of five contexts resident, the dominant failure is a wrong context rather than a miss, so Hit@3-style residency metrics say little in this configuration. Random ranking also had no cold misses but was correct only 20.7\% of the time.

\subsection{Hysteresis}
\label{sec:eval_hysteresis}
\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{hysteresis_churn.pdf}
\caption{States loaded per day against hysteresis margin $\Delta$ (100 synthetic days each). The share of correct interactions stayed at 98.5\% (normal) and 90.6\% (high noise) across all margins up to 0.5.}
\label{fig:hysteresis}
\end{figure}

Fig.~\ref{fig:hysteresis} varies $\Delta$ with everything else fixed. Raising $\Delta$ from 0 to the deployed 0.10 halved loads per day under normal noise (65.9 to 31.6) and cut them from 297.5 to 106.2 under high noise. The share of correct interactions did not change for any margin up to 0.5, presumably because a change of context moves scores by more than these margins. Each load is a restore or, if the cache file is missing, a full prefill, so the margin mainly saves background work. On these traces a margin of 0.3 would cut loads further at no cost in accuracy; we keep 0.10 until real traces are available, since a larger margin also delays switching after a genuine but small change in evidence.

\subsection{Not Measured}
We did not measure battery drain, power, temperature or CPU frequency for the 60-second sweep, the 15-minute job or background priming. Each load in Table~\ref{tab:prediction} is a unit of background work whose energy cost remains to be quantified on the device.

\section{Threat Model}
\label{sec:threat}

\textbf{Assets.} The choice of context that shapes what the device says for its user, and the cached KV files, which encode the context prompts.

\textbf{Adversaries.} (A) An app on the same phone supplying mock locations. (B) Someone nearby advertising BLE beacons that copy registered anchors. (C) Someone with access to the phone's files or backups. Ordinary sensor noise and stale fixes are covered by the evaluation above.

\textbf{What an attacker can do.} The router only ranks the five pre-written contexts. Sensor manipulation can therefore make the app use the wrong one of them, but it cannot add a context, change a prompt, or alter the user's intent. This bounds the damage without removing it: a wrong context still changes what the model writes for the user.

\textbf{Mitigations and residual risk.} Location fixes flagged as mock by Android are rejected, as are stale fixes and implausible accuracy values. When the mock flag is set, forged GPS had little effect (1.7\% wrong context, Table~\ref{tab:prediction}). On a rooted phone a forged fix need not carry the flag; if it also reports a plausible accuracy such as 5~m, the checks accept it, and the wrong-context rate rose to 38.9\%. BLE advertisements are unauthenticated and we have no defence against cloned beacons (9.9\% wrong context); the router has no check that GPS and BLE agree. Cache files are stored unencrypted in app-private storage and are excluded from backup and device transfer, which protects them only as far as the Android sandbox does.

\textbf{Out of scope.} Rooted or compromised operating systems, kernel or firmware attackers, and physical extraction of storage.

\section{Limitations and Conclusion}
\label{sec:conclusion}

The latency results come from one phone, one 0.5B model and 30 trials per condition, with a single cached context size; restore time for longer contexts, end-to-end latency without interference, memory use under the current slot layout, and an independent llama.cpp throughput benchmark on the same phone remain to be measured. The prediction results come from synthetic traces whose schedule matches the contexts' time anchors and do not model priming delay; real multi-day sensor recordings are needed to confirm them. The prototype has five hand-written contexts. Energy cost is unmeasured. Nothing here has been evaluated with AAC users, and no clinical claim is made.

Within those limits, the measurements separate the parts of the question. Restoring a primed context removed most of the matched prefill cost (351 versus 2507~ms, 2.4~ms restore). Sensor-driven residency used the correct context for 98.5\% of synthetic interactions, compared with 92.2\% for request-driven LRU, by trading first-visit misses for 1.5\% wrong-context answers. Undetected GPS forgery is the main weakness: it raised wrong-context answers to 38.9\%.

The code, benchmark logs, evaluation harness and figure scripts are available at \url{https://github.com/omni-ar/AACBridge}.
