\begin{abstract}
On-device language models often need situational context prepended to the user's input: location, nearby people, time of day. The prefill step that reads this context is expensive. On a OnePlus~11R running Qwen2.5-0.5B-Instruct (Q4\_K\_M), prefilling a 439-token context prompt took 14.9~s. Server systems cache KV state across users to skip repeated prefill, but that depends on overlapping requests from multiple users, which a single phone does not have. A phone does have sensors. CAP-KVC uses GPS, BLE proximity, and time of day to rank a small set of pre-written contexts, prefills the likely ones during idle time, and keeps up to three as resident llama.cpp KV state. At interaction time only the user's intent tokens are decoded. With a cached 44-token context, the CAP-KVC prefill step (9 intent tokens) averaged 366~ms versus 1847~ms for the matched 52-token inline condition, a 5.0$\times$ reduction ($n=30$ each, interleaved randomized trial order); the KV state restore added 2.9~ms. Over 100 synthetic days with five contexts, correct-context selection reached 98.5\% of 6,400 interactions versus 92.2\% for request-driven LRU caching, at a cost of 1.5\% wrong-context selections. Undetected GPS forgery raised wrong-context selections to 38.9\%. One device, one model, five contexts, synthetic traces.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
In order for a language model to respond effectively to a question or task posed by a user from their smartphone, it needs to know where the user is physically located as well as other factors about the user's environment---for instance, who else may be in the user's vicinity and what time of day it currently is. Take an AAC (augmentative and alternative communication) app~\cite{beukelman2020}: the user taps ``I need water,'' and the app has to expand that into a full sentence. But what it should say depends on the setting. A hospital ward at 11~a.m.\ calls for different phrasing than home in the evening with a caregiver present, so the context has to be there. The standard approach is to prepend a context description to the intent and let the model read both.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
However, feeding this information into the language model prior to submitting a query is very costly. We found that on an Android-based smartphone, populating a 439-token input prompt took 14.2~s (Section~\ref{sec:eval_latency}). Even a short 52-token prompt took 2.5~s, which works out to roughly 30~ms per token. For someone who communicates through the device, that kind of delay comes up every single turn.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
Server-based systems sidestep these repeated prefills using a shared key-value (KV) store to maintain state across multiple user requests. SGLang keeps prompt prefixes in a radix tree~\cite{sglang}, vLLM shares KV blocks between requests~\cite{vllm}, Prompt Cache stores attention states for reusable prompt modules~\cite{promptcache}, and RAGCache caches the KV state of retrieved documents~\cite{ragcache}. These systems rely on request overlap from multiple users: one user's prefill populates the cache, and a later user's matching request skips it. A single phone has no such overlap. The request that would populate the cache is the user's own first turn in a new setting, and that turn pays the full prefill cost.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
While there is no stream of requests coming from a phone, the device does have sensors available to help inform which context the user is likely going to want. In this paper we propose CAP-KVC (Context-Aware Predictive KV-Cache priming). It makes predictions on the best few context descriptions based upon the user's current location (via GPS), who or what else is nearby (via Bluetooth Low Energy, or BLE, proximity), and what time of day it is. While the phone is in idle mode it prefills those predicted contexts the user is most likely to want next. Once prefilled, the phone stores up to three of them as llama.cpp KV state. When the user decides to interact with the device, only their intent tokens need to be decoded. On a OnePlus~11R running Qwen2.5-0.5B-Instruct (Q4\_K\_M), we measured that restoring an existing 44-token context as opposed to prefilling it---parsing all of its tokens inline---takes 351~ms vs.\ 2507~ms respectively (7.1$\times$, $n=30$ each). Restoring the actual state takes 2.4~ms.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
Our study was performed over a synthetic period of 100 days of sensor data for five different contexts. The routing and residency policies were able to determine the correct context for 98.5\% of 6,400 interactions generated during that time frame, compared with 92.2\% for a request-driven cache with no ability to leverage sensing capabilities, which misses on every first visit. The evaluation is limited to a single device, a single model, five contexts, and synthetic traces.

This paper makes three contributions. First, a sensor-driven predictive KV caching design for a single user on a phone: deterministic context scoring from GPS, BLE and time-of-day readings, a bounded resident set with hysteresis-gated replacement, and a two-tier fallback for cold misses. Second, an Android implementation built on llama.cpp through JNI, with per-slot KV residency, rollback of each interaction so a resident state can be reused unchanged, crash-safe cache persistence via atomic file renames, and location input validation. Third, an evaluation that separates the restore benefit (matched-context latency) from prediction quality (trace-driven comparison against oracle, request-driven, random and single-sensor baselines) and from adversarial sensor input (forged GPS and cloned BLE beacons).

\section{Related Work}
\label{sec:related}

\textbf{Reusing KV state across requests.}
SGLang~\cite{sglang} stores prompt prefixes in a radix tree; vLLM~\cite{vllm} shares KV blocks via paged memory; Prompt Cache~\cite{promptcache} precomputes attention states for reusable prompt modules; CacheBlend~\cite{cacheblend} fuses cached non-prefix chunks; CacheGen~\cite{cachegen} compresses KV for cross-server transfer; RAGCache~\cite{ragcache} caches per-document KV with retrieval-aware eviction. All populate the cache when a request containing the relevant prefix arrives, and the payoff requires later requests with overlapping content. RAGCache is closest to CAP-KVC in that it caches document-specific KV state, but it remains reactive: the first request bearing a document pays full prefill. On a single phone, there is no request stream from other users. CAP-KVC populates the cache \emph{before} any request, using sensor evidence rather than request content (Table~\ref{tab:positioning}). Section~\ref{sec:eval_prediction} simulates a request-driven LRU policy on the same traces. The KV save/load mechanism itself is provided by llama.cpp~\cite{llamacpp}; our contribution is choosing \emph{which} context to prepare, \emph{when}, and from \emph{what} signals.

\textbf{Shrinking the KV cache.} H$_2$O~\cite{h2o} and Scissorhands~\cite{scissorhands} evict less important tokens; SnapKV~\cite{snapkv} compresses keys and values; StreamingLLM~\cite{streamingllm} keeps only attention sinks and recent tokens; KVQuant~\cite{kvquant} quantizes the stored state. These reduce memory within a sequence. They are orthogonal to what we do---a compressed KV state can still be primed and restored.

\textbf{On-device inference.} Quantization~\cite{dettmers2022,frantar2022}, small-model design~\cite{mobilellm}, runtimes like llama.cpp~\cite{llamacpp} and MLC-LLM~\cite{mlcllm}, flash offloading~\cite{llminaflash}, and heterogeneous NPU/CPU execution~\cite{powerinfer2} have collectively made it feasible to run language models on a phone. They lower the cost of processing each token, but they do not get rid of the context prefill that happens before the first output token. That is the gap CAP-KVC is meant to address.

\subsection{Problem}
Let $C=\{c_1,\dots,c_M\}$ be pre-written contexts with prompts $p_i$ of $N_i$ tokens. In the straightforward approach (the retrieval-augmented style), the device decodes the full $p_i$ followed by the user's intent $q$ on every request; prefill cost grows with $N_i+|q|$. CAP-KVC moves the prefill of $p_i$ to idle time and stores the resulting KV state. At interaction time the device restores that state and decodes only $q$.

The question is which contexts to prepare, since memory allows only $K<M$ of them to be resident at once. Our prototype has $M=5$ contexts (home morning, home evening, hospital ward, therapy room, caregiver visit) and $K=3$ resident slots.

\subsection{Context Scoring}
\label{sec:scoring}
% --- HUMAN-SCORED BLOCK: equations and setup, preserve ---
Each context $c_i$ is associated with an expected hour of day $t_i$, an anchor GPS location $\ell_i$, and a set of BLE beacon anchors $A_i$ with weights $w_{ij}$. When a sensor reading comes in, the system computes a score for each context:
\begin{equation}
S(c_i)=\alpha S_{\mathrm{time}}+\beta S_{\mathrm{gps}}+\gamma S_{\mathrm{ble}},\qquad \alpha+\beta+\gamma=1,
\label{eq:score}
\end{equation}
where each component captures one kind of sensor evidence:
\begin{align}
S_{\mathrm{time}}&=\exp\!\bigl(-d_{\mathrm{circ}}(t,t_i)^2/2\sigma^2\bigr),\quad \sigma=2~\mathrm{h},\\
S_{\mathrm{gps}}&=\exp\!\bigl(-d_{\mathrm{hav}}(\ell,\ell_i)/\lambda\bigr),\quad \lambda=0.1~\mathrm{km},\\
S_{\mathrm{ble}}&=\textstyle\sum_{j\in A_i} w_{ij}\,\mathbb{1}[j\ \mathrm{seen}] \big/ \sum_{j\in A_i} w_{ij}.
\end{align}
$d_{\mathrm{circ}}$ wraps around midnight so that 11:55~p.m.\ and 12:05~a.m.\ are treated as ten minutes apart rather than nearly 24 hours. $S_{\mathrm{gps}}$ uses the Haversine distance and falls to 0.37 at 100~m. The BLE score is the weighted fraction of expected beacons that the device actually detected.

The weights $\alpha$, $\beta$, $\gamma$ are not learned---they come from a per-sensor reliability heuristic. Time gets a fixed $w_t=0.4$. GPS gets $w_g=\exp(-a/50~\mathrm{m})$ for reported accuracy $a$ (0 without a fix). BLE gets $w_b$ equal to the mean of $1/(1+e^{-0.1(r+70)})$ over the observed RSSI values $r$ (0 when no beacons are detected). These are normalized to sum to one. Contexts scoring below 0.01 are dropped. ``Predictive'' in the title refers to preparing a context before the request, not to a trained model.

\subsection{Residency and Hysteresis}
\label{sec:residency}
At most $K=3$ KV states can be resident. With five contexts, three slots cover the majority of transitions while bounding background priming work. Section~\ref{sec:eval_k_ablation} evaluates $K\in\{1,2,3\}$.

After each sweep the scorer ranks all contexts. Candidates already resident stay. A new candidate takes a free slot if one exists; if all three are occupied, it replaces the weakest resident only when its score exceeds the weakest's by more than $\Delta$. Without a margin, noisy GPS accuracy and intermittent BLE detection caused repeated state swaps between sweeps. $K$ denotes the number of resident KV states. $\Delta$ is a replacement margin on scores and is independent of $K$. The deployed value is $\Delta=0.10$; Section~\ref{sec:eval_hysteresis} measures its effect.

The same replacement rule runs in the 60-second sweep and in a 15-minute background check that omits BLE scanning and may only add the top-ranked context.

\subsection{Interaction and Fallback}
When the user interacts, the app picks the highest-ranked resident context from the latest sweep. If one exists, the device resumes that state and decodes only the intent. If no ranked context is resident (a cold miss), a canned response goes out immediately (Tier~1) and priming of the top-ranked contexts starts in the background (Tier~2). A wrong-context answer is the other failure mode: a resident context is used but does not match the user's actual situation.

\section{Implementation}
\label{sec:implementation}

AACBridge is an Android app (Kotlin, API~26+, \texttt{arm64-v8a}) that uses llama.cpp~\cite{llamacpp} through JNI. The model is Qwen2.5-0.5B-Instruct~\cite{qwen25} quantized to Q4\_K\_M; we chose it as the smallest instruction-tuned model available in llama.cpp's GGUF format that fits within the phone's memory constraints.

\textbf{Native boundary.} 14 JNI methods, all scalar arguments and results: lifecycle (initialize backend, load model, release), KV operations (save, load, clear scratch, reset slot), inference (inline run, prefill only, resume), and four timing getters (prefill~ms, generation~ms, prompt tokens, generated tokens). A single \texttt{ReentrantLock} serializes every native call; llama.cpp context state is shared and not thread-safe.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
\textbf{Sequence slots.} We set up the llama.cpp context with four sequences of 1024 tokens each. Three of these are reserved for resident states, and the fourth serves as a scratch space for inline inference and benchmark runs. We added the scratch sequence specifically so that running a benchmark or doing inline inference would not disturb a resident state that was already loaded.

Priming decodes the context into its assigned slot and serializes the slot to a temporary file, then renames atomically (no partial cache file on crash). Resuming appends the intent at the slot's current position, generates the response, then strips everything past the cached boundary---rolling the slot back so the resident state is reused unchanged next time.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
With 24 layers, 2 KV heads of dimension 64, and fp16 storage, Qwen2.5-0.5B needs 12~KiB of KV data per token. The four sequences reserve 48~MiB at context creation. We did not re-measure process memory after this layout change.

% --- HUMAN-SCORED BLOCK: preserve verbatim ---
\textbf{Sensing.} A foreground service runs the sensor sweep every 60~s. Each sweep performs a 3-second BLE scan and requests a location fix. Every location provider's last fix is checked before the system trusts it: the fix must not be flagged as mock by the Android OS, it must be at most 120~s old, and the reported accuracy must fall between 2 and 500~m. If nothing passes, one fresh fix is requested (network provider preferred over GPS for speed). A WorkManager job runs every 15 minutes without BLE.

\textbf{Intent input.} On-screen buttons or gaze-dwell interface. An sEMG+gaze fusion classifier from earlier work is included as a prototype input but not evaluated here.

\textbf{Backup.} App backup disabled. KV cache directory excluded from cloud backup and device-to-device transfer.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Setup}
% --- HUMAN-SCORED BLOCK: preserve verbatim ---
All latency measurements were taken on a OnePlus~11R (Snapdragon~8+~Gen~1, 8~GB RAM, Android~14), with 4 threads, batch size 512, greedy decoding, and a cap of 64 output tokens. Trials used an interleaved protocol: each of the 30 measured rounds ran all six conditions once in a seeded random order (seed 20261005), preceded by 2 warmup rounds (discarded). This spreads thermal drift and OS scheduling noise across conditions instead of concentrating them on whichever block runs last. The benchmark sets an \texttt{isBenchmarkActive} flag that causes the gaze interface to reject all interaction requests during measurement; 336 gaze events were blocked, zero leaked through. Per-trial battery temperature, thermal-zone temperature (65.8--78.0$^\circ$C, median 69.7$^\circ$C), and big-core (cpu7) frequency (787--1402~MHz) were logged. Prefill and generation times come from \texttt{std::chrono} timestamps placed around the \texttt{llama\_decode} call in native code; restore time is measured around the load call. All 180 trials and the analysis script are in the repository.

\subsection{Matched-Context Latency}
\label{sec:eval_latency}
This experiment measures the prefill cost removed when a previously prepared context is restored rather than decoded from scratch.

The CAP-KVC condition holds a 44-token context in its cache. The matched inline condition decodes the same context plus the intent as a single 52-token prompt. Larger inline conditions (89, 206, and 439 tokens) show how inline prefill scales; their ratios relative to CAP-KVC grow by construction since the inline prompts are longer, and they are not matched comparisons.

Table~\ref{tab:latency} shows the results. The KV restore overhead (loading the cached state from disk) averaged 2.9~ms (median 2.1~ms). The CAP-KVC prefill (decoding only the 9 intent tokens after restore) averaged 366~ms (SD 122). The matched inline prefill (all 52 tokens) averaged 1847~ms (SD 510). The ratio is 5.0$\times$ (Welch $t(32.3)=15.5$, $p<10^{-15}$).

A rough time to first token (restore + prefill + one generation step) is about 0.37~s for CAP-KVC, about 1.8~s inline.

Inline prefill grew at about 30~ms per prompt token (OLS, $R^2=0.87$; Fig.~\ref{fig:prefill}), reaching 14.9~s at 439 tokens where the CAP-KVC prefill was 40.8$\times$ shorter. That larger ratio reflects the cost CAP-KVC avoids when contexts happen to be long, not a matched speedup. We only measured restore for the 44-token cache and cannot say how it scales with context length.

The prefill saving should be kept in perspective. Generation dominated the full response: 3.9--5.7~s at median with 64 output tokens. So the 1.5~s saved in matched prefill shortens the overall response by much less than 5.0$\times$; the benefit is concentrated in time to first token. Generation times varied across conditions and trials (IQRs above 2~s). Position-in-round showed negligible correlation with prefill (Spearman $|\rho|<0.13$ for all conditions), confirming the interleaved design controlled for ordering effects. Thermal-zone temperature was weakly correlated with prefill ($|\rho|<0.30$), and the zone-temperature range across all 180 trials was 65.8--78.0$^\circ$C. The big core (cpu7) ran at its maximum frequency (1.4~GHz) in 68\% of trials and throttled to 787~MHz or below in 11\%.

\subsection{Prediction and Cache Policy}
\label{sec:eval_prediction}
\textbf{Traces.} We do not have recorded sensor traces from real users, so we generated synthetic ones (seed 42). Each of 100 simulated days follows the five-context routine 06:00--22:00, with each context boundary shifted per day by $U(\pm0.5~\mathrm{h})$. A sweep runs every simulated minute; an interaction fires every 15 minutes (6,400 interactions total). Per-sweep noise parameters: GPS displacement $\mathcal{N}(0,50~\mathrm{m})$, GPS dropout 10\%, reported accuracy $\mathcal{N}(15,10)$~m, per-beacon detection 80\% with RSSI $\mathcal{N}(-65,10)$~dBm, BLE outage 15\%, spurious beacon 10\%. The high-noise variant: $\pm1.5$~h boundary shifts, 200~m GPS displacement, 30\% GPS dropout, 50~m accuracy, 50\% detection, 40\% BLE outage. The context time anchors were written from the same daily routine that the traces follow, so time-of-day evidence is favourable by construction. Section~\ref{sec:eval_independent} evaluates schedules with shifted and jittered boundaries using independent seeds.

\textbf{Simulation.} The trace evaluator runs the production scoring, residency and selection code (the same code deployed on the phone). It does not model priming delay: a state chosen at one sweep is assumed usable by the next simulated minute.

\textbf{Metrics.} For each interaction, let $c^\ast$ be the true context and $\hat{c}$ be the one the system actually used. Correct: $\hat{c}=c^\ast$. Wrong context: $\hat{c}\neq c^\ast$ (the system picked a resident context but the wrong one). Cold miss: no ranked context is resident. These partition every interaction into exactly one outcome. Loads per day counts how many times a state was primed or restored into the resident set---a measure of background work.

\textbf{Baselines.} \emph{Oracle}: $c^\ast$ always resident (upper bound). \emph{Request-driven LRU}: no sensing; the correct context becomes known only at request time, is used if cached, otherwise is a cold miss and enters a three-entry LRU cache persisting across days. \emph{Random}: uniform random scores per sweep, same residency rule. \emph{Single sensor}: time only; GPS only or BLE only with $w_t=0.001$ so time does not leak through normalization.

With all sensors, the deployed rules picked the correct context 98.5\% of the time (Table~\ref{tab:prediction}).

Request-driven LRU scored 92.2\% correct and never selected a wrong context---by definition, since it only uses a context it has verified. Its 7.8\% failure rate is entirely cold misses. Five contexts visited in order with three cache entries means every first visit after the cache fills is a miss. Sensing eliminated those first-visit misses, but introduced 1.5\% wrong-context selections.

GPS alone could not separate the three contexts at the home location. BLE alone left the system with no candidate in 0.5\% of interactions (no registered beacon detected). Time alone reached 92.2\%, but that number reflects how the traces were built---the time anchors match the daily schedule---not a property we would expect from real user schedules.

Cold misses were near zero for every sensing policy. The router's top-1 accuracy matched the share of correct interactions in every configuration. With three of five contexts always resident, the dominant failure mode is a wrong selection rather than a miss, so Hit@3-style metrics carry little information here. Random ranking also had no cold misses (three of five are always resident) but was correct only 20.7\% of the time.

\subsection{Hysteresis}
\label{sec:eval_hysteresis}
\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{hysteresis_churn.pdf}
\caption{States loaded per day against hysteresis margin $\Delta$ (100 synthetic days each). The share of correct interactions stayed at 98.5\% (normal) and 90.6\% (high noise) across all margins up to 0.5.}
\label{fig:hysteresis}
\end{figure}

Fig.~\ref{fig:hysteresis} shows what happened when we varied $\Delta$ with everything else held fixed. Raising $\Delta$ from 0 to the deployed 0.10 halved loads per day under normal noise (65.9 to 31.6) and cut them from 297.5 to 106.2 under high noise. Accuracy did not change at any margin up to 0.5---consistent with the interpretation that genuine context changes move the scores by much more than these margins. Each load is a disk restore or (if the cache file is missing) a full prefill, so the margin mainly saves background work. A margin of 0.3 would reduce loads further on these traces at no accuracy cost, but we keep 0.10 until real traces are available; a larger margin also delays switching when sensor evidence shifts by a small but genuine amount.

\subsection{Markov Successor Baseline}
\label{sec:eval_markov}
A deterministic five-context routine visited in the same order every day is trivially predictable: the successor of \texttt{home\_morning} is always \texttt{hospital\_ward}. We trained a first-order Markov chain $P(\text{next}\mid\text{current})$ on the first 50 days and tested on the remaining 50. The Markov predictor achieved 99.7\% correct context selection with only 6.0 loads/day, compared with 98.5\% correct and 31.6 loads/day for the full CAP-KVC router. This result is expected: on these synthetic traces, context ordering is perfectly deterministic, and the Markov baseline exploits this structure without any sensor input. On real schedules with skipped, reordered, or interrupted contexts, the advantage would diminish. We report this baseline to make the ceiling explicit.

\subsection{Residency Capacity ($K$) Ablation}
\label{sec:eval_k_ablation}
With $K=1$, the system carries a single resident state and changes it at every transition: 99.4\% correct, 0.6\% wrong context, 10.7 loads/day. With $K=2$: 98.5\% correct, 1.5\% wrong, 39.1 loads/day. With $K=3$ (deployed): 98.5\% correct, 1.5\% wrong, 31.6 loads/day. $K=1$ achieves the highest accuracy because every slot change is a deliberate transition to the current best state, with no stale residents competing. However, every transition requires a load (restore or prime), and each load costs seconds of background work. $K=3$ amortizes loads across transitions: the new context is often already resident from a previous sweep. On these traces, accuracy is equivalent for $K \ge 2$.

\subsection{Multi-Seed Evaluation}
\label{sec:eval_multiseed}
To test robustness to noise realization, we ran the full router on 20 independent seeds (each 100 days, normal noise). Correct-context rate ranged from 98.0\% (seed~8) to 98.6\% (seed~19), mean 98.3\%, SD 0.15 pp. LRU was constant at 92.2\% (deterministic given the schedule). The advantage of sensing over LRU ($+$6.1 pp mean) was stable across all seeds.

\subsection{Independent Trace Schedules}
\label{sec:eval_independent}
We tested robustness to schedule variation using traces with $\pm$1 h boundary shifts (5 seeds), $\pm$2 h shifts, doubled interaction frequency (7-minute intervals), and combined high jitter ($\pm$1.5 h, 150 m GPS). Mean correct rates: 97.7\% ($\pm$1 h), 95.6\% ($\pm$2 h), 98.3\% (variable dwell), 95.9\% (high jitter). Performance degrades predictably with boundary ambiguity: at $\pm$2 h shifts, context boundaries overlap more with adjacent time anchors, and the wrong-context rate rises to 4.3\% (vs.\ 1.5\% at $\pm$0.5 h).

\subsection{Abstention and Risk-Coverage}
\label{sec:eval_risk}
If the score gap between the top-ranked and second-ranked context is small, the system could abstain (fall back to Tier-1 generic response). We sweep a margin threshold $\tau$ from 0 to 0.20. At $\tau=0$ (no abstention): 98.5\% correct, 1.5\% wrong. At $\tau=0.05$: 97.1\% correct, 0.8\% wrong, 2.1\% abstention. At $\tau=0.10$: 94.6\% correct, 0.4\% wrong, 4.9\% abstention. The abstention mechanism trades correct selections for a reduction in wrong-context responses. Whether this trade-off is worthwhile depends on the cost of wrong context versus no context, which is application-specific. CAP-KVC does not currently use abstention; these results show it is available if needed.

\subsection{Not Measured}
Battery drain, power, temperature, CPU frequency: unmeasured for the 60-second sweep, the 15-minute job, and background priming. Each load in Table~\ref{tab:prediction} is a unit of background work whose energy cost we have not been able to quantify.

\section{Threat Model}
\label{sec:threat}

Two assets matter: the context selection (it determines what the device says for the user) and the cached KV files (they encode the full context prompts).

We consider three attackers. (A)~An app on the same phone supplying mock locations via Android's API. (B)~Someone nearby broadcasting BLE beacons that clone registered anchor identifiers. (C)~Someone with file-level access to the phone or backups.

\textbf{Scope of attack.} The router only ranks the five pre-written contexts. Sensor manipulation can force a wrong selection but cannot add a context, change a prompt, or alter the user's intent. A wrong context still changes what the model produces, so the damage is bounded but not eliminated.

\textbf{Mitigations and residual risk.} We reject location fixes flagged as mock by Android, along with stale fixes and those with reported accuracy outside 2--500~m. With the mock flag working, forged GPS had almost no effect (1.7\% wrong context, Table~\ref{tab:prediction}). On a rooted phone a forged fix need not carry the flag; if it also reports plausible accuracy (e.g.\ 5~m), our checks accept it, and the wrong-context rate reached 38.9\%. BLE advertisements are unauthenticated---anyone can broadcast any beacon identifier---and we have no defence against cloned beacons (9.9\% wrong context). The router does not cross-check GPS against BLE. Cache files are stored unencrypted in app-private storage, excluded from backup and device transfer; protection extends only as far as the Android sandbox.

\textbf{Out of scope.} Rooted/compromised OS, kernel or firmware attackers, physical extraction of storage.

\section{Limitations and Conclusion}
\label{sec:conclusion}

The latency measurements come from one phone (OnePlus~11R), one 0.5B-parameter model, 30 trials per condition, one cached context size. Restore time was measured only for a 44-token cache; we do not know how it scales with context length. The benchmark ran on a debug build. It used interleaved randomized trial order and blocked interaction inference during measurement (Section~\ref{sec:evaluation}); thermal-zone temperature was logged per trial but battery temperature was not readable (returned $-1$). Memory footprint with the model loaded and three resident KV states: 627~MB proportional (PSS), of which 151~MB native heap (llama.cpp context and KV tensors) and 391~MB memory-mapped model file. On the 8~GB OnePlus~11R this leaves headroom but constrains multi-tasking; smaller models or KV compression would reduce it. The prediction results come from synthetic traces whose time anchors match the contexts' schedule; on these traces, a Markov successor baseline that uses no sensors at all achieves 99.7\% correct (Section~\ref{sec:eval_markov}), exposing that the deterministic schedule is trivially predictable. The simulation does not model priming delay---a context chosen at one sweep is assumed available at the next. Real multi-day sensor recordings from actual users are needed. Five hand-written contexts. Energy cost unmeasured. No evaluation with AAC users. No clinical claim.

Within those limits, the measurements do separate the parts of the question. The KV restore overhead was 2.9~ms; the matched prefill dropped from 1847~ms to 366~ms. Sensor-driven residency selected the correct context for 98.5\% of synthetic interactions (mean 98.3\% across 20 seeds, SD 0.15~pp; Section~\ref{sec:eval_multiseed}), compared with 92.2\% for request-driven LRU, by trading first-visit cold misses for 1.5\% wrong-context selections. With $\pm$2~h schedule jitter, accuracy degraded to 95.6\% (Section~\ref{sec:eval_independent}). Abstention at $\tau=0.05$ reduced wrong-context responses from 1.5\% to 0.8\% at the cost of 2.1\% cold misses (Section~\ref{sec:eval_risk}). The main vulnerability is undetected GPS forgery, which raised wrong-context answers to 38.9\%.

Code, benchmark logs, evaluation harness, and figure scripts are available at \url{https://github.com/omni-ar/AACBridge}.
