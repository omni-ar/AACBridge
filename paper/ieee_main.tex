\begin{abstract}
On-device language models frequently require situational context---physical location, proximate companions, time of day---prepended to user prompts to generate appropriate responses. Ingesting this context on mobile hardware is computationally expensive. On a OnePlus~11R running Qwen2.5-0.5B-Instruct (Q4\_K\_M), prefilling a 439-token context prompt averaged 14.9~s. Server systems cache key-value (KV) states across queries to avoid recomputation, but that mechanism relies on concurrent request streams from multiple users that do not exist on a personal smartphone. A smartphone does possess ambient sensors. CAP-KVC uses GPS, Bluetooth Low Energy (BLE) proximity, and time-of-day readings to rank a small set of pre-authored situational contexts, prefills likely candidates during device idle periods, and retains up to three resident llama.cpp sequence states. When an interaction occurs, the engine decodes only the user's intent tokens. Across 30 interleaved trials per condition in randomized order, restoring a 44-token context and decoding 9 intent tokens averaged 366~ms, compared with 1847~ms for the matched 52-token inline prefill (a 5.0$\times$ reduction; Welch $t(32.3)=15.5$, $p<10^{-15}$). State restoration added 2.9~ms. Over 100 simulated days spanning 6,400 interactions across five contexts, sensor-driven residency selected the correct context for 98.5\% of interactions (mean 98.3\%, SD 0.16~pp across 20 seeds) versus 92.2\% for request-driven LRU caching, trading first-visit cold misses for 1.5\% wrong-context selections. A deterministic Markov baseline reached 99.7\%, reflecting the predictability of synthetic schedules. Undetected GPS spoofing increased wrong-context selections to 38.9\%. The prototype is evaluated on one phone, one model, five contexts, and synthetic traces.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

When a smartphone runs an on-device language model to assist a user, generating an appropriate response often requires situational context: the user's physical location, nearby companions, and the time of day. In augmentative and alternative communication (AAC)~\cite{beukelman2020}, for example, an individual may tap a short prompt like ``need water.'' Expanding that brief input into a contextually appropriate utterance depends on the environment. A hospital ward at mid-morning calls for different phrasing than home in the evening with family present. The conventional method prepends a descriptive context prompt to the user's intent tokens and processes the entire sequence through the model.

Ingesting these context prompts on mobile processors incurs substantial latency before generation begins. On an Android smartphone (OnePlus~11R) running Qwen2.5-0.5B-Instruct quantized to Q4\_K\_M, evaluating a 439-token context prompt required an average of 14.9~s (Section~\ref{sec:eval_latency}). Even a compact 52-token prompt required 1.8~s, corresponding to roughly 34~ms per prompt token. In conversational turn-taking, an initial delay of nearly two seconds before speech output begins disrupts natural communication.

Server-based serving engines avoid re-evaluating prompt prefixes by retaining intermediate key-value (KV) attention states across requests. Radix-tree caching in SGLang~\cite{sglang}, paged KV sharing in vLLM~\cite{vllm}, modular attention reuse in Prompt Cache~\cite{promptcache}, and retrieved-passage caching in RAGCache~\cite{ragcache} exploit query overlap across thousands of users. One user's request populates the cache; subsequent users matching that prefix skip the prefill stage. A personal smartphone lacks multi-user request concurrency. The query that would populate a reactive cache is the user's first turn in a newly entered environment, forcing that interaction to bear the full prefill delay.

While a smartphone receives no external query stream, it continuously gathers ambient sensor data. We exploit this observation in CAP-KVC (Context-Aware Predictive Key-Value Cache priming). CAP-KVC uses GPS coordinates, BLE proximity to beacon anchors, and the device clock to score and rank a small library of pre-written situational contexts. During idle periods, the application prefills high-ranking contexts into native llama.cpp sequence slots and saves their KV states to private storage, maintaining up to three resident states in memory. When the user interacts via button tap or gaze dwell, the engine resumes the active resident slot and decodes only the intent tokens. On the OnePlus~11R, restoring an existing 44-token context and decoding 9 intent tokens averaged 366~ms, compared with 1847~ms for the matched 52-token inline prefill (a 5.0$\times$ reduction, $n=30$ each; Welch $t(32.3)=15.5$, $p<10^{-15}$). Deserializing the cached state from storage added an average overhead of 2.9~ms (median 2.1~ms).

We evaluated context selection across 100 simulated days containing 6,400 user interactions across five daily contexts. Sensor-driven residency selected the correct context for 98.5\% of interactions, compared with 92.2\% for a request-driven LRU cache that misses on every context transition. The sensor approach trades cold misses for a 1.5\% rate of wrong-context selections. This evaluation is subject to specific constraints: one physical phone, one model architecture, five candidate contexts, and synthetic traces.

This paper makes three contributions:
\begin{enumerate}
\item A sensor-driven predictive KV caching architecture for single-user mobile inference: deterministic multi-modal context scoring from GPS, BLE, and clock inputs, bounded slot residency governed by a hysteresis threshold, and a two-tier fallback mechanism.
\item An Android implementation built on llama.cpp via JNI, featuring sequence-slot isolation, rollback of user intent tokens so primed contexts remain reusable, atomic disk serialization, and location validation filters.
\item An evaluation characterizing matched-context prefill latency through randomized interleaved benchmarking, prediction accuracy across noisy and jittered synthetic traces, baselines including an empirical Markov ceiling, and resilience against forged sensor inputs.
\end{enumerate}

\section{Related Work}
\label{sec:related}

\textbf{Request-driven KV reuse.}
Serving frameworks for large language models amortize prompt computation by caching KV tensors in host or accelerator memory. SGLang~\cite{sglang} indexes KV tensors using a radix tree over token prefixes; vLLM~\cite{vllm} allocates KV memory in fixed-size pages to support prefix sharing; Prompt Cache~\cite{promptcache} and CacheBlend~\cite{cacheblend} precompute and fuse attention states for modular prompt components; CacheGen~\cite{cachegen} compresses KV tensors for streaming across servers; RAGCache~\cite{ragcache} structures cache replacement around document retrieval patterns. These frameworks operate reactively: a cache entry is populated only after a request containing those specific tokens arrives at the server. Cache utility depends on multi-user query concurrency. On a single smartphone, no concurrent query stream exists. The initial query in a newly visited context must execute a full prefill before any state can be cached (Table~\ref{tab:positioning}). CAP-KVC alters the trigger and timing of cache population: it prefills KV states proactively during idle time based on physical sensor readings, before any interaction begins.

\textbf{KV cache compression.}
A separate research direction aims to reduce the memory footprint of attention states during inference. Heavy-hitter pruning in H$_2$O~\cite{h2o} and Scissorhands~\cite{scissorhands}, attention-sink retention in StreamingLLM~\cite{streamingllm}, key-value reduction in SnapKV~\cite{snapkv}, and low-precision representations in KVQuant~\cite{kvquant} reduce storage within an active sequence. These methods address intra-sequence memory consumption and bandwidth. They do not eliminate the prefill computation needed to read an initial prompt. Compression techniques are orthogonal to our design: a compressed KV tensor representation can still be primed and restored using the proactive caching mechanisms described in this work.

\textbf{On-device inference runtimes.}
Post-training quantization~\cite{dettmers2022,frantar2022}, mobile-optimized model architectures like MobileLLM~\cite{mobilellm}, embedded runtime engines such as llama.cpp~\cite{llamacpp} and MLC-LLM~\cite{mlcllm}, flash-memory parameter offloading~\cite{llminaflash}, and heterogeneous CPU/NPU execution~\cite{powerinfer2} enable sub-billion-parameter language models to execute on mobile silicon. These runtimes accelerate per-token decode throughput. However, prefilling several dozen or hundred context tokens before the first token can be decoded remains a major latency bottleneck on mobile CPUs. CAP-KVC builds on llama.cpp to remove this prefill overhead from the interactive path.

A background service sweeps onboard sensors periodically, scores each candidate context, and updates the set of resident KV states. \subsection{Data Management}
The application stores a fixed catalog of $M=5$ pre-written situational contexts: home morning, home evening, hospital ward, therapy room, and caregiver visit. Each context $c_i$ defines a system prompt $p_i$ averaging 44 tokens (specifying persona, spatial environment, and vocabulary guidelines). The system also maintains serialized KV cache dumps (`.kv` files) in app-private internal storage, ensuring persisted states can be loaded across process restarts.

\subsection{Context Scoring}
\label{sec:scoring}
Each context $c_i$ defines an expected time anchor $t_i$, a reference GPS coordinate $\ell_i$, and a list of expected BLE beacon identifiers $A_i$ with importance weights $w_{ij}$. When the background service gathers sensor inputs, it computes a score for each context:
\begin{equation}
S(c_i)=\alpha S_{\mathrm{time}}+\beta S_{\mathrm{gps}}+\gamma S_{\mathrm{ble}},\qquad \alpha+\beta+\gamma=1,
\label{eq:score}
\end{equation}
where each modal score evaluates a specific sensor dimension:
\begin{align}
S_{\mathrm{time}}&=\exp\!\bigl(-d_{\mathrm{circ}}(t,t_i)^2/2\sigma^2\bigr),\quad \sigma=2~\mathrm{h},\\
S_{\mathrm{gps}}&=\exp\!\bigl(-d_{\mathrm{hav}}(\ell,\ell_i)/\lambda\bigr),\quad \lambda=0.1~\mathrm{km},\\
S_{\mathrm{ble}}&=\textstyle\sum_{j\in A_i} w_{ij}\,\mathbb{1}[j\ \mathrm{seen}] \big/ \sum_{j\in A_i} w_{ij}.
\end{align}
The circular distance $d_{\mathrm{circ}}$ wraps around midnight (treating 11:55~p.m.\ and 12:05~a.m.\ as 10 minutes apart). The spatial score $S_{\mathrm{gps}}$ applies the Haversine distance $d_{\mathrm{hav}}$, decaying to 0.37 at a displacement of 100~m. The BLE score $S_{\mathrm{ble}}$ measures the detection ratio of expected beacon anchors.

The combination weights $\alpha$, $\beta$, and $\gamma$ derive from dynamic sensor quality indicators rather than learned parameters. Time receives a constant weight $w_t=0.4$. GPS accuracy $a$ (in meters) scales the location weight as $w_g=\exp(-a/50~\mathrm{m})$, falling to zero if no location fix is returned. BLE confidence $w_b$ averages the logistic mapping $1/(1+e^{-0.1(r+70)})$ over detected beacon RSSI values $r$, setting $w_b=0$ if no beacons appear. Normalizing these values yields $\alpha, \beta, \gamma$. Contexts whose aggregate score falls below 0.01 are discarded. In this paper, ``predictive'' refers to proactively prefilling states prior to interaction rather than executing a statistical machine learning classifier.

\subsection{Residency Management and Hysteresis}
\label{sec:residency}
Device RAM constrains resident capacity to $K=3$ contexts out of $M=5$. The llama.cpp context reserves four sequence slots: three for resident states and one scratch slot.

Following each sweep, the router sorts all candidates by score. Contexts that are already resident retain their slots. If an unprimed context qualifies for residency and an unoccupied slot exists, it is loaded into that slot. When all three slots are occupied, a new candidate evicts the lowest-ranking resident only if its score exceeds the incumbent's score by more than a hysteresis threshold $\Delta$:
\begin{equation}
S(c_{\mathrm{new}}) > S(c_{\mathrm{resident\_min}}) + \Delta.
\end{equation}
Without this hysteresis margin, minor GPS jitter or intermittent BLE packet drops cause repeated cache evictions between consecutive sweeps. The parameter $K$ controls residency capacity; $\Delta$ is an independent score difference threshold. The deployed prototype sets $\Delta=0.10$. Section~\ref{sec:eval_hysteresis} analyzes the impact of varying this threshold.

\subsection{Priming, Interaction, and Fallback}
\label{sec:fallback}
Priming executes during idle time. The engine decodes the 44-token prompt into an assigned sequence slot, writes the resulting KV tensors to a temporary file on disk, and renames the file atomically. This guarantees that process crashes do not leave corrupted or partially written cache files. A background WorkManager task wakes every 15 minutes to evaluate coarse location and time without running the BLE radio, ensuring that top contexts remain primed without excessive battery draw.

When the user provides an intent input, the app checks the resident slots for the highest-scoring candidate. If a matching resident state is available, the engine appends the user's intent tokens $q$ to that slot, generates the response, and then rolls the slot back by discarding tokens added during generation. This rollback preserves the primed context state for subsequent turns.

If the router's top-ranked context is not resident in memory (a cold miss), a two-tier fallback responds:
\begin{itemize}
\item \textbf{Tier 1:} A canned acknowledgment is rendered immediately on screen and passed to the text-to-speech engine.
\item \textbf{Tier 2:} The system schedules a background prefill of the missing context into an available sequence slot.
\end{itemize}
If sensor noise or spoofing causes the system to select an incorrect resident context, the model decodes the user's intent against that wrong template. Because the candidate pool is restricted to five vetted clinical contexts, the resulting text remains bounded to the application's domain rather than generating unconstrained output.

\section{Implementation}
\label{sec:implementation}

AACBridge is implemented as an Android application (Kotlin, targetSdk 34, minSdk 26, compiled for \texttt{arm64-v8a}). Inference is handled by a native C++ module embedding llama.cpp~\cite{llamacpp}. The target model is Qwen2.5-0.5B-Instruct~\cite{qwen25} in Q4\_K\_M GGUF format, chosen as a compact instruction-tuned model compatible with mobile memory limits.

\textbf{JNI Interface.}
The native boundary in \texttt{llama\_jni.cpp} exports 14 native functions to Kotlin: three lifecycle operations (\texttt{initializeBackend}, \texttt{initializeModel}, \texttt{release}); four KV cache operations (\texttt{saveKVCache}, \texttt{loadKVCache}, \texttt{clearKVCache}, \texttt{resetSlot}); three inference functions (\texttt{runInference}, \texttt{prefillOnly}, \texttt{resumeInference}); and four telemetry getters (\texttt{getLastPrefillMs}, \texttt{getLastGenMs}, \texttt{getLastPromptTokens}, \texttt{getLastGenTokens}). All native calls pass through a single \texttt{ReentrantLock} in Kotlin because internal llama.cpp execution contexts are not thread-safe.

\textbf{Sequence Allocation.}
The llama.cpp context is initialized with four sequence slots of 1024 tokens each. Slots 0, 1, and 2 hold resident context states; slot 3 serves as an isolated scratch buffer for inline inference and benchmarking, preventing inline executions from invalidating resident KV states. Qwen2.5-0.5B contains 24 transformer layers with 2 KV heads of dimension 64. Using 16-bit floating point storage, KV data consumes 12~KiB per token, totaling 48~MiB allocated across the four sequence slots at initialization. Prior to this sequence slot restructuring, a system memory snapshot recorded 627~MB proportional set size (PSS), including 151~MB native heap and 391~MB memory-mapped model weights; memory was not re-measured after moving to the four-sequence slot layout.

\textbf{Sensor Processing.}
A foreground service executes the sensor sweep every 60~s, performing a 3-second BLE scan via \texttt{BluetoothLeScanner} and querying \texttt{FusedLocationProviderClient}. The implementation validates location fixes before acceptance: fixes flagged as mock by Android (\texttt{isMock()} or \texttt{isFromMockProvider()}) are rejected, fixes older than 120~s are discarded, and reported accuracy must fall between 2~m and 500~m. If cached fixes fail validation, a fresh network or GPS fix is requested. An auxiliary WorkManager job executes every 15 minutes without BLE.

\textbf{Intent Input and Security.}
The user interface supports touch buttons and gaze-dwell input. Application backup is disabled (\texttt{android:allowBackup="false"}), and \texttt{data\_extraction\_rules.xml} excludes the KV cache directory from device-to-device transfers and cloud storage.

\section{Evaluation}
\label{sec:evaluation}

\subsection{Experimental Setup}
\label{sec:eval_setup}
All latency benchmarks were performed on a OnePlus~11R smartphone (Qualcomm Snapdragon~8+~Gen~1, 8~GB LPDDR5 RAM, Android~14). The llama.cpp engine was configured with 4 compute threads, batch size 512, greedy decoding, and a cap of 64 generated tokens. The benchmark used a debug build.

To mitigate thermal throttling bias and operating system background scheduling noise, measurements followed an interleaved protocol. The benchmark executed 30 rounds; each round evaluated all six test conditions in a randomized sequence governed by seed 20261005, preceded by 2 discarded warmup rounds. Gaze input was isolated during testing by setting an \texttt{isBenchmarkActive} guard: 336 gaze events were intercepted and blocked, with zero leakage into the inference pipeline. Every trial logged device telemetry: thermal-zone temperature ranged between 65.8$^\circ$C and 78.0$^\circ$C (median 69.7$^\circ$C); big-core (cpu7) frequency ranged between 787~MHz and 1402~MHz, operating at its 1.4~GHz maximum in 68\% of trials and throttling below 1000~MHz in 11\%; battery temperature returned $-1.0$ (unsupported on this build without system privileges). Prefill and generation durations were measured using \texttt{std::chrono} timestamps surrounding \texttt{llama\_decode}; restore time was recorded around the cache load operation. All 180 trial logs are preserved in the repository.

\subsection{Matched-Context Latency}
\label{sec:eval_latency}
We measured the execution latency removed when a primed context is restored rather than decoded inline from raw text.

In the CAP-KVC condition, a 44-token context prompt resides in memory; the model decodes only the 9 intent tokens. In the matched inline condition, the identical 44-token context and 9 intent tokens are processed together as a single 52-token prompt. Additional inline conditions (89, 206, and 439 tokens) illustrate scaling behavior as context size expands.

Table~\ref{tab:latency} summarizes the latency breakdown. The overhead of loading a serialized KV state from internal storage averaged 2.9~ms (median 2.1~ms). Prefilling the 9 intent tokens in CAP-KVC averaged 366~ms (SD 122~ms; median 293~ms). In contrast, the matched 52-token inline prefill averaged 1847~ms (SD 510~ms; median 1741~ms). This represents a 5.0$\times$ reduction in prefill time (Welch $t(32.3)=15.5$, $p<10^{-15}$). Estimated time to first token (restore plus prefill plus an initial generation step) dropped from approximately 1.8~s inline to 0.37~s with CAP-KVC.

Inline prefill latency scaled at an empirical rate of 34.1~ms per prompt token (ordinary least squares, $R^2=0.88$; Fig.~\ref{fig:prefill}). At 439 tokens, inline prefill reached an average of 14,941~ms (14.9~s; median 13,989~ms), which is 40.8$\times$ longer than the CAP-KVC 9-token prefill. This 40.8$\times$ figure reflects the latency avoided when handling longer prompts rather than a matched speedup. Restore latency was benchmarked solely for the 44-token context state; scaling across variable cache sizes was not evaluated.

Autoregressive token generation dominated overall interaction time, spanning a median of 3.9~s to 5.7~s across conditions when generating up to 64 tokens. Consequently, saving 1.5~s during prefill does not produce a 5.0$\times$ reduction in total end-to-end response time; the benefit is isolated to time to first token. Trial position within an interleaved round showed low correlation with prefill latency (Spearman $|\rho| \le 0.13$ across conditions), confirming that the randomized interleaved protocol successfully controlled for ordering bias. Thermal-zone temperature exhibited moderate correlation with prefill ($|\rho| \le 0.30$).

\subsection{Prediction and Cache Policy}
\label{sec:eval_prediction}
\textbf{Traces.}
Because multi-day physical sensor traces from individuals using AAC were unavailable, we generated synthetic traces (seed 42). The simulation models 100 days following a five-context routine between 06:00 and 22:00, with context transition times perturbed daily by uniform jitter $U(\pm 0.5~\mathrm{h})$. A sensor sweep occurs every minute; an interaction is generated every 15 minutes (totaling 6,400 interactions). Baseline noise parameters include: Gaussian GPS displacement $\mathcal{N}(0, 50~\mathrm{m})$, 10\% GPS fix dropouts, reported GPS accuracy $\mathcal{N}(15, 10)~\mathrm{m}$, 80\% per-beacon detection with RSSI $\mathcal{N}(-65, 10)~\mathrm{dBm}$, 15\% BLE scan failure, and 10\% spurious beacon sightings. A high-noise scenario applies $\pm 1.5~\mathrm{h}$ transition jitter, 200~m GPS displacement, 30\% GPS dropouts, 50~m reported accuracy, 50\% BLE detection, and 40\% BLE scan outages. Because the context time anchors align with the simulated schedule, temporal evidence is structurally favorable.

\textbf{Simulation.}
The trace harness executes the production Kotlin router and residency policy. Priming delay is not simulated: contexts scheduled for residency at one sweep are assumed available by the subsequent simulated minute.

\textbf{Metrics.}
For each interaction, let $c^\ast$ denote the true environment context and $\hat{c}$ the context selected by the system. Interactions are partitioned into three mutually exclusive outcomes: \emph{correct} ($\hat{c} = c^\ast$); \emph{wrong context} ($\hat{c} \neq c^\ast$, where a resident context was used but did not match ground truth); and \emph{cold miss} (no candidate context was resident in memory). \emph{Loads per day} measures how many times a context was primed or restored into a resident slot, reflecting background compute activity.

\textbf{Baselines.}
We evaluated four comparison baselines: \emph{Oracle} ($c^\ast$ always resident, theoretical upper bound); \emph{request-driven LRU} (sensing disabled; true context revealed only upon interaction, cached in a 3-slot LRU cache); \emph{random ranking} (uniform random scores per sweep under the deployed residency rule); and \emph{single-sensor ablations} (time-only scoring; GPS-only and BLE-only scoring with $w_t = 0.001$ to prevent temporal leakage through score normalization).

With all sensors active, the deployed configuration selected the correct context for 98.5\% of interactions (Table~\ref{tab:prediction}). Request-driven LRU reached 92.2\% correct and incurred zero wrong-context errors, since it only caches verified requests; its 7.8\% failure rate consisted entirely of cold misses on first visits. Sensor-driven priming eliminated first-visit cold misses at the cost of 1.5\% wrong-context selections.

GPS alone could not differentiate the three contexts situated at the home location (morning, evening, caregiver visit), yielding 87.9\% accuracy. BLE alone suffered cold misses in 0.5\% of interactions where no registered beacon was detected. Time alone reached 92.2\%, though this high figure is an artifact of synthetic schedule construction.

\subsection{Hysteresis Margin Sweep}
\label{sec:eval_hysteresis}
\begin{figure}[t]
\centering
\includegraphics[width=0.88\columnwidth]{hysteresis_churn.pdf}

Fig.~\ref{fig:hysteresis} evaluates the effect of varying the hysteresis margin $\Delta \in [0.00, 0.50]$. Increasing $\Delta$ from 0.00 to the deployed 0.10 reduced loads per day from 65.9 to 31.6 under normal noise, and from 297.5 to 106.2 under high noise. Context accuracy remained unchanged at 98.5\% (normal) and 90.6\% (high noise) across margins up to 0.50, demonstrating that genuine context transitions generate score shifts larger than these margins. While larger margins would reduce loads further on these synthetic traces, we maintain $\Delta = 0.10$ to preserve sensitivity to subtle transitions on real-world inputs.

\subsection{Markov Successor Baseline}
\label{sec:eval_markov}
Because the synthetic routine visits five contexts in a fixed sequence, transitions are deterministic: \texttt{home\_morning} is consistently followed by \texttt{hospital\_ward}. We trained a first-order Markov model $P(c_{t+1} \mid c_t)$ on the first 50 days and evaluated it on the final 50 days. The Markov predictor attained 99.7\% accuracy with 6.0 loads per day, exceeding the full sensor router (98.5\% correct, 31.6 loads/day).

This result demonstrates that the synthetic benchmark schedule is trivially predictable; the Markov baseline exploits this fixed structure without requiring sensor inputs. On irregular real-world schedules containing skipped, delayed, or out-of-order visits, Markov transition probabilities would degrade. We report this baseline to make the predictability ceiling explicit.

\subsection{Residency Capacity (\texorpdfstring{$K$}{K}) Ablation}
\label{sec:eval_k_ablation}
We varied resident slot capacity across $K \in \{1, 2, 3\}$. With $K=1$, the system maintains a single resident state, switching at every transition: accuracy reached 99.4\% (0.6\% wrong context) with 10.7 loads per day. Because only one context is held, there is no competition from stale resident states. However, every context transition requires a prefill or restore operation. With $K=2$, accuracy was 98.5\% (1.5\% wrong context) with 39.1 loads per day. With $K=3$ (deployed), accuracy remained 98.5\% while loads per day decreased to 31.6, as incoming contexts frequently already occupied a resident slot.

\subsection{Multi-Seed Robustness}
\label{sec:eval_multiseed}
To examine sensitivity to random noise generation, we evaluated the full router across 20 independent random seeds (each spanning 100 days under standard noise). Correct context selection averaged 98.3\% (SD 0.16~pp), ranging from 98.03\% (seed~8) to 98.58\% (seed~4). LRU accuracy remained constant at 92.19\% across all seeds due to the deterministic schedule. The performance advantage of sensor-driven residency over LRU remained steady at $+6.1$~pp across seeds.

\subsection{Schedule Variation}
\label{sec:eval_independent}
We tested robustness against irregular schedules using traces with $\pm 1.0~\mathrm{h}$ boundary jitter (5 seeds), $\pm 2.0~\mathrm{h}$ jitter, doubled interaction rates (7-minute intervals), and combined high jitter ($\pm 1.5~\mathrm{h}$ jitter with 150~m GPS noise). Mean accuracy was 97.7\% ($\pm 1.0~\mathrm{h}$), 95.6\% ($\pm 2.0~\mathrm{h}$), 98.3\% (variable dwell), and 95.9\% (combined high jitter). As temporal boundaries become ambiguous under $\pm 2.0~\mathrm{h}$ shifts, wrong-context selections rose to 4.4\% (compared with 1.5\% under $\pm 0.5~\mathrm{h}$ jitter).

\subsection{Abstention and Risk-Coverage}
\label{sec:eval_risk}
When the score margin between the top two candidate contexts is narrow, the router can abstain from selecting a resident context and trigger Tier-1 canned responses. Sweeping an abstention margin threshold $\tau$ from 0.00 to 0.20 showed: at $\tau = 0.00$ (no abstention), 98.5\% correct, 1.5\% wrong context, 0.0\% abstention; at $\tau = 0.05$, 97.1\% correct, 0.8\% wrong context, 2.1\% abstention; at $\tau = 0.10$, 94.6\% correct, 0.4\% wrong context, 4.9\% abstention. Abstention trades correct responses to suppress wrong-context selections. The prototype does not enable abstention by default, as the preferred balance between wrong context and generic canned responses is application-specific.

\subsection{Security Experiments}
\label{sec:eval_security}
We evaluated router behavior under simulated GPS spoofing and BLE beacon cloning. When forged GPS fixes reported plausible coordinates (at 5~m accuracy) without the Android mock location flag, wrong-context selection rose to 38.9\% (Table~\ref{tab:prediction}). When Android's mock location flag was detected, the router rejected the fix and fell back to valid sensors, reducing wrong selections to 1.7\%. Cloned BLE beacons produced a 9.9\% wrong-context rate, as BLE advertisements are unauthenticated.

\subsection{Resource Overhead and Unmeasured Quantities}
\label{sec:eval_unmeasured}
Physical energy consumption and battery drain attributable to the 60-second sensor sweep, the 15-minute background worker, and native priming were not measured with external power instrumentation. The memory footprint of 627~MB PSS (151~MB native heap, 391~MB memory-mapped model) represents a snapshot taken before configuring four sequence slots. Cache restore scaling across arbitrary token lengths was not measured.

\section{Threat Model}
\label{sec:threat}

The threat model considers two primary assets: the integrity of context selection (preventing adversarial manipulation of spoken utterances) and the confidentiality of serialized KV cache files (which encode prompt text).

We analyze three attacker profiles: \emph{Attacker~A (software mock location)}, an unprivileged application on the same device advertising spoofed GPS coordinates through Android location APIs; \emph{Attacker~B (physical radio impersonation)}, an adversary in physical proximity transmitting spoofed BLE advertisements matching registered beacon identifiers; and \emph{Attacker~C (storage extraction)}, an entity attempting to inspect or extract cached files from device storage or backups.

\textbf{Security Boundaries and Mitigations.}
The router limits selection strictly to the catalog of five pre-authored contexts; sensor manipulation cannot inject arbitrary prompt text or alter user intent. Attacker~A is mitigated by checking Android's mock location flags (\texttt{isMock()} and \texttt{isFromMockProvider()}) and filtering anomalous accuracy readings; under active mock detection, wrong-context selection dropped to 1.7\%. Against Attacker~B, unauthenticated BLE beacons cannot be cryptographically verified; multi-modal scoring provides partial mitigation (9.9\% wrong context under cloned beacons). Against Attacker~C, KV files are isolated within application-private storage with backup disabled (\texttt{android:allowBackup="false"}), protecting cache contents unless the device operating system is rooted or physically compromised.

\section{Limitations and Conclusion}
\label{sec:conclusion}

This study has several limitations: (1)~Benchmarks evaluate a single device (OnePlus~11R, Snapdragon~8+~Gen~1) running one quantized model (Qwen2.5-0.5B-Instruct); cross-device portability across different mobile chipsets remains unmeasured. (2)~The prototype uses five pre-written contexts over synthetic behavioral traces; while the Markov baseline reaches 99.7\% accuracy on this deterministic schedule, performance on irregular human mobility traces requires physical validation. (3)~Trace simulations assume scheduled contexts are instantly available at the subsequent sweep, omitting runtime priming contention. (4)~Background battery drain was not evaluated with a hardware power monitor. (5)~The system was not tested with individuals who use AAC, and makes no clinical efficacy claims.

Within these constraints, the measurements demonstrate that proactive sensor-driven KV cache priming decouples context prompt prefill from user interaction on a smartphone. Across 30 randomized interleaved trials, CAP-KVC reduced matched 52-token prefill latency from 1847~ms to 366~ms (a 5.0$\times$ reduction; Welch $t(32.3)=15.5$, $p<10^{-15}$), while state restoration added 2.9~ms. In trace simulations over 100 days, sensor-guided residency achieved 98.5\% correct context selection versus 92.2\% for request-driven LRU caching, trading cold misses on first visits for a 1.5\% wrong-context rate. The primary vulnerability remains undetected GPS spoofing, which elevated wrong-context selections to 38.9\%.

Source code, benchmark logs, and evaluation scripts are available at \url{https://github.com/omni-ar/AACBridge}.
